## Goal

The reminder time a ḥāfiẓ sees is rendered through the app's **one presentation boundary** — never formatted ad hoc in a widget. This task fills the formatted-string slot E18-T06's `ReminderRow` left open: a single time-of-day formatting entry point in the l10n/presentation layer (beside the `CalendarPresenter` / `numberFormatFor(locale)` family, eng-07 §4) that maps E18-T02's persisted `reminderMinutesSinceMidnight` integer to a localized time run — **Extended Arabic-Indic** digits (۰۱۲, U+06F0–U+06F9) for `fa`/`ckb`, **Arabic-Indic** (٠١٢, U+0660–U+0669) for `ar` — with the numeral remap **downstream** of any conversion and the mixed run **FSI/PDI-isolated** (`isolateLtr`, LRI…PDI) so it never reorders inside RTL chrome. No raw ASCII digit ever reaches the UI (PRD §13.3), and the reminder time renders in the user's numerals per design-system 10 §10. This is purely on-screen **display**: E18-T04 computes the *scheduling* fire instant (a machine `TZDateTime`) and the two never share a code path — nothing here touches `timezone`, `flutter_local_notifications`, an instant, or a clock. A time-of-day is calendar-invariant, so the `CalendarSystem` choice affects only the *surrounding date presentation* the presenter already owns — the load-bearing part here is the numeral remap and the isolation, not a calendar conversion.

## Implementation notes

This task is a pure display transform: no persistence, no OS call, no clock, no copy. It is a localization-correctness surface → the digit-codepoint and isolation tests are **written first**.

1. **Files.** One entry point in the l10n/presentation layer, beside the `numberFormatFor(locale)` / `CalendarPresenter` family (e.g. `packages/l10n/lib/src/reminder_time_format.dart`, or a method on the presenter file — final placement per the workspace layout): e.g. `String formatReminderTime({required int minutesSinceMidnight, required Locale locale})`. Plus the one-line call-site change in E18-T06's row/picker slot. No other file formats a time anywhere in the repo.
2. **Input discipline.** Split `minutesSinceMidnight` into hour/minute **integers** (`~/ 60`, `% 60`) — plain integer arithmetic, mirroring eng-07 §2. Never construct a local `DateTime` instant from it (the DST off-by-one class, eng-07 §3); if a locale time *pattern* is taken from `intl`'s `DateFormat`, feed it a pure `DateTime.utc(1970, 1, 1, h, m)` used strictly as a formatting calculator (the same pure-`(y,m,d)`-not-a-clock trick eng-07 §4's presenter uses) — never `DateTime.now()`, never `.toLocal()`.
3. **Convert first, remap numerals last.** Whatever produces the shaped run (locale hour/minute order, the separator, a localized dayPeriod if the locale pattern carries one), its numeric fields pass through `numberFormatFor(locale)` **after** conversion — the pinned tags `fa-u-nu-arabext` / `ckb-u-nu-arabext` / `ar-u-nu-arab`, minute zero-padded via the formatter (`minimumIntegerDigits: 2`), never a hand `padLeft` on ASCII then string-replace. A run reaching a widget with an ASCII digit is the defect this task exists to prevent (eng-07 §4; PRD §13.3).
4. **Isolate the run.** Wrap the finished time run with the one bidi helper owned by eng-rtl-and-bidi-layout — `isolateLtr` (LRI…PDI), since a digit run's direction is known (impl-12 §4; never first-strong FSI here, never legacy LRE/RLO). The row's standalone displayed value is the isolated run in a single `Text`; where T10's sentences embed it, it is passed as an already-formatted, already-isolated ARB placeholder — never spliced.
5. **Calendar-invariance.** A time-of-day is identical under Jalālī, Umm al-Qurā, and Gregorian; this entry point takes no `CalendarSystem` and performs no calendar conversion. Any *date* shown near the row (none is specified by T06) would go through the existing `CalendarPresenter.format` — out of scope here. Rendering mutates nothing: the stored minutes integer, prefs row, and engine state are untouched by any re-render or locale/calendar switch (ui-numerals-calendar-text pattern 5).
6. **The widget stays dumb.** E18-T06's row and picker echo call this entry point with the committed prefs value and the active locale — no `"$h:$m"`, no `TimeOfDay.format(context)` / `MaterialLocalizations.formatTimeOfDay` as the display path (their digit emission is not pinned to the `-u-nu-` tags), no formatting logic in any widget file. The Material time-picker dialog's *internal* dial digits are framework chrome outside this task; the value this app displays is ours and goes through the boundary.
7. **Strict T04 firewall.** No `timezone`, `flutter_timezone`, `flutter_local_notifications`, `TZDateTime`, or fire-moment symbol in any file this task adds (grep-verifiable). Display and scheduling consume the same persisted integer through two disjoint paths; a shared helper between them is a design error, not a reuse win.
8. **Docs.** Every public API carries `///` docs stating: input is a civil time-of-day integer (0–1439), output is a locale-numeralled, bidi-isolated display run; it is not a scheduling value and must never feed one (eng-write-to-coding-standards conventions).
9. **Pitfalls to avoid:** remapping digits *before* building the run (then the pattern re-introduces ASCII); trusting a bare `fa`/`ar` sublocale default instead of the pinned `-u-nu-` tag; one numeral set for all three locales (fa showing ٤٥٦ is a user-visible defect); hand string-replacing ASCII digits; hard-splicing `":"` between two separately-isolated fragments (isolate the whole run, once); FSI on a known-direction run; formatting in the widget "just for the preview"; reading `DateTime.now()` or constructing a local instant; letting this helper grow a `TZDateTime` overload "for convenience".

## Acceptance criteria

- [ ] Exactly one time-of-day formatting entry point exists in the l10n/presentation layer beside the `CalendarPresenter`/`numberFormatFor` family; the E18-T06 row's displayed time and the picker's in-row echoed value both render through it; grep shows no time-formatting logic (`"$h:$m"`-style splice, `TimeOfDay.format`, `padLeft` on digits) in any widget file.
- [ ] For a fixed prefs value, the rendered run under `fa` and `ckb` contains only Extended Arabic-Indic digits (U+06F0–U+06F9) and under `ar` only Arabic-Indic digits (U+0660–U+0669); **no ASCII digit (U+0030–U+0039) appears in any rendered time run in any locale** — asserted on actual codepoints.
- [ ] The numbering system is pinned on the locale tag (`fa-u-nu-arabext` / `ckb-u-nu-arabext` / `ar-u-nu-arab`) via the shared `numberFormatFor(locale)` path; the numeral remap sits downstream of the pattern/conversion step; minute zero-padding is produced by the formatter, not ASCII `padLeft`.
- [ ] The finished time run is wrapped by the one bidi-isolation helper as a known-direction run (`isolateLtr`, LRI…PDI — not FSI, not legacy controls) and enters any T10 sentence as a formatted, isolated placeholder in a single `Text`/`TextSpan` — never a spliced substring; under RTL the run never reorders against its surrounding copy.
- [ ] Rendering is a pure display transform: the stored `reminderMinutesSinceMidnight`, the prefs row, and all engine state are byte-identical across renders, locale switches, and `CalendarSystem` switches; the rendered time string itself is identical under all three calendar systems.
- [ ] No file this task adds imports `timezone`, `flutter_timezone`, or `flutter_local_notifications`, constructs a `TZDateTime`, calls `DateTime.now()`/`.toLocal()`, or computes a fire moment (grep-verifiable); T04's scheduling path is untouched.
- [ ] Every public API added carries `///` docs naming the civil time-of-day input semantics and the display-only contract; `dart format`/`dart analyze` clean.

## Tests

All deterministic and offline by construction — fixed integer inputs, fixed locales, no clock (nothing here needs the injected `today`, and no `DateTime.now()` exists to leak); authored per eng-write-dart-test, sharing the localization gate (PRD §20 gate 5). Codepoint/structure assertions live here; the pixel golden is E18-T11's.

- `l10n/test/reminder_time_format_test.dart` (unit) — **written first**:
  - a fixed value (e.g. 1295 → 21:35) renders with only U+06F0-range digits for `fa` and `ckb` and only U+0660-range digits for `ar` — asserting the exact expected codepoints, and asserting **no** U+0030–U+0039 anywhere in the output;
  - the run is wrapped LRI…PDI (`isolateLtr`), exactly once, around the whole run — no nested/fragmented isolates, no FSI, no LRE/RLE/LRO/RLO;
  - minute zero-padding (e.g. 540 → 09:00-shaped) pads with locale digits, not ASCII;
  - an exhaustive sweep over all 1440 minute values × three locales asserts no ASCII digit ever appears (the cheap property that pins the downstream-remap law);
  - the same input formatted under `CalendarSystem.jalali` / `hijriUmmAlQura` / `gregorian` contexts yields an identical time string (calendar-invariance).
- `features/test/reminders/reminder_time_display_test.dart` (widget) — pumps the E18-T06 row with a fixed `ReminderPreferences` under `fa`/`ckb`/`ar`: the displayed time run shows the correct digit block per locale (codepoint assertion on the rendered `Text` data); a stub/spy on the presentation entry point proves the widget obtained its string from the boundary and built none itself; re-rendering after a locale switch leaves the prefs value untouched (recording repository asserts zero writes).
- Grep guards (CI): no `timezone`/`flutter_timezone`/`flutter_local_notifications`/`TZDateTime` import and no `DateTime.now()` in this task's files; no `TimeOfDay.format(`/`formatTimeOfDay(` call site in the reminder feature; no string-interpolation digit splice in `ReminderRow`.
