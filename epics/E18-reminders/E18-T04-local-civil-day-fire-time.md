## Goal

The correctness heart of the epic's date-safety risk: one **pure, frozen-vector-pinned function at the app-notification edge** that maps the persisted reminder time-of-day (E18-T02's `reminderMinutesSinceMidnight`, already schema-`CHECK`ed to 0–1439) plus the **injected local civil day** to the DST-correct local fire instant — the `TZDateTime` that `zonedSchedule` ultimately consumes (engineering README tech-decision log, decision 14) — surfaced across the boundary as E18-T01's framework-free fire-moment value shape, so the daily reminder never drifts a day (or an hour) across a DST or timezone transition, exactly as a `due_at` never may. The function reads no clock: "now" / "today" / the local `tz.Location` enter **once**, as explicit parameters resolved at the injected clock boundary (eng-define-service-boundary item 6); the day advance is `CalendarDate.addDays(1)` integer math, never `Duration` arithmetic on an instant (eng-07 §2); and the result keys off the device's **local civil day** — never a UTC date and never a Hijri date being exact (eng-07 §6). **Test-first**: the DST/timezone vector suite is written before the function body. This task *derives* the instant only — executing the schedule is E18-T01, deciding *when* to recompute is E18-T05, and rendering the chosen time for *display* is E18-T07. No user-facing copy or number is authored here, so no `CLAIMS.md` row applies.

## Implementation notes

This is app-edge pure math: no OS call, no persistence, no widget, no string, no clock read. It is the one function in the epic where a wrong branch silently breaks the "never drifts a day" promise, so the vectors come first.

1. **File**: `app/lib/notifications/reminder_fire_time.dart` — in the **app shell**, beside the E18-T01 live impl, inside the one module T01's banned-import scan permits to import `timezone` (decision 14 quarantines the dep to this edge). It must **not** live in `engine/`, `models/`, or the `CalendarDate` core — the engine never sees a zone (eng-07 §5 pitfalls). Imports: `package:timezone` types, `CalendarDate`, and T01's fire-moment value type only; no Flutter, no plugin symbol, no I/O.
2. **Shape (design intent)**: one pure top-level function, e.g. `nextReminderFire({required int minutesSinceMidnight, required CalendarDate today, required DateTime now, required tz.Location location})` returning T01's fire-moment value. Every input is explicit; there is no zero-argument overload, no default that reads a clock, and no `tz.local` inside the body. The split `hour = m ~/ 60`, `minute = m % 60` happens here, once.
3. **Semantics**: build the candidate as `tz.TZDateTime(location, today.year, today.month, today.day, hour, minute)`. If the candidate is strictly after `now`, fire today; otherwise advance the **civil day** — `today.addDays(1)` — and rebuild the `TZDateTime` from the new `(y, m, d, hour, minute)`. The wall-clock time is *reconstructed per day in the local zone*; the day is *advanced as an integer*. Never `candidate.add(Duration(days: 1))` — across a spring-forward that fires at 08:00 instead of 07:00, the exact bug class §2 exists to kill.
4. **The output conforms to T01's value shape.** The computed `TZDateTime`'s resolved civil fields plus the location's IANA id are transcribed into the framework-free DTO T01 defined beside its interface; the T01 live impl rebuilds the identical `TZDateTime` 1:1 for `zonedSchedule`. No `TZDateTime` crosses the T01 interface; both the derivation and the transcription are deterministic, pinned by a round-trip vector.
5. **DST gap and ambiguity are pinned, not assumed.** A chosen time inside a spring-forward gap (e.g. 02:30 on the transition date) does not exist; the `TZDateTime` constructor normalizes it — the vector pins that the fire stays on the **same civil day** (shifted forward), never the previous or next day. A fall-back ambiguous time (e.g. 01:30 occurring twice) resolves to one deterministic offset — pinned by a frozen vector so a `timezone`-package upgrade that changes it fails loudly.
6. **One coherent clock read.** The caller (E18-T05) resolves `now`, `today = todayFor(now)`, and the device `location` (via `flutter_timezone` → `tz.getLocation`, inside E18-T01's edge) **once** and passes them together. Pitfall: deriving `today` and `now` from two separate reads can straddle a midnight rollover and skip or double a day — the function's contract states the triple must come from a single boundary read.
7. **`location` is an explicit parameter, never `tz.local`.** Tests pass `tz.getLocation('Asia/Tehran')` etc. from the bundled tz database, so every vector is byte-identical under any host timezone; only the live edge (E18-T01/T05) resolves the device's actual zone.
8. **No UTC round-trip, no Hijri.** The instant is constructed directly from local civil `(y, m, d, hh, mm)`; never build a UTC `DateTime` and convert, and never derive the fire day from a `CalendarPresenter`/Hijri/Jalālī conversion (eng-07 §6 — display calendars never feed math).
9. **Extend the CI clock grep** (eng-07 §5): `DateTime.now()`, `TZDateTime.now(`, and `tz.local` are banned in the fire-time path outside the single injected-clock edge; this file must pass with zero hits.
10. **Out of scope — do not creep**: calling `zonedSchedule`, `matchDateTimeComponents`, notification ids/channels, or Android inexact mode (E18-T01); prefs shape/validation (E18-T02); persist-before-republish (E18-T03); cancel-and-reschedule orchestration (E18-T05); any rendered time string (E18-T07). This task adds no dependency beyond what decision 14 already approved.

## Acceptance criteria

- [ ] `app/lib/notifications/reminder_fire_time.dart` exists in the app shell (not `engine/`, not `models/`), exporting one pure function from `(minutesSinceMidnight, today, now, location)` to the fire moment; it imports `package:timezone` types, `CalendarDate`, and T01's value type only — no Flutter, no `flutter_local_notifications`, no I/O (verifiable by grep over the file).
- [ ] The function reads no clock and no ambient zone: zero occurrences of `DateTime.now()`, `TZDateTime.now`, or `tz.local` in the fire-time path; the CI clock grep covers this module and passes.
- [ ] Same-day vs next-day is decided by comparing the candidate instant to the injected `now`; the next-day advance is `CalendarDate.addDays(1)` with the `TZDateTime` rebuilt from civil fields — no `Duration` arithmetic on an instant anywhere in the path.
- [ ] The output conforms to E18-T01's framework-free fire-moment value shape, and the DTO → `TZDateTime` transcription round-trip is identity (pinned by a vector) — the instant `zonedSchedule` receives is exactly the instant derived here.
- [ ] Across a spring-forward and a fall-back transition, the fire **civil day** never shifts: the local wall-clock time of the result equals the chosen time-of-day (except the pinned gap normalization, which stays on the same civil day) and the fire day is always `today` or `today.addDays(1)` — proven by frozen vectors, not by inspection.
- [ ] The fire instant derives from the local civil day only — no UTC date component and no Hijri/Jalālī value participates in the computation.
- [ ] The full vector suite is byte-identical under different host timezones (run under at least a DST zone and a no-DST zone, per eng-07 §7 T4/T5 — never green only under `TZ=UTC`).
- [ ] The suite was written first (red on a stub), and the frozen expected rows are committed; CI verifies them and never regenerates them.
- [ ] All added Dart passes `dart format --set-exit-if-changed` and `dart analyze --fatal-infos`, with `///` docs on the public function stating the single-boundary-read contract.

## Tests

All pure-Dart, deterministic, offline by construction: fixed injected `(now, today)`, explicit `tz.Location` from the bundled tz database, and the shared throwing-`HttpOverrides` bootstrap (this path opens no socket) — per eng-write-dart-test.

- `app/test/notifications/reminder_fire_time_vectors_test.dart` — **written first**: a frozen table of `(minutesSinceMidnight, today, now, location) → expected fire instant` (asserted as ISO-8601 with UTC offset), covering: now-before-chosen-time (fires today) and now-after (fires `today.addDays(1)`); the exact-equality edge (`now` == candidate → tomorrow, strictly-after contract); the 0 (midnight) and 1439 (23:59) boundary values; a spring-forward gap time (normalized, same civil day); a fall-back ambiguous time (one pinned offset); a `today` on the transition date where the *next* fire crosses the transition (wall time still the chosen time, civil day advances exactly 1); representative zones — `Asia/Tehran` (historic DST), `America/New_York` (current DST), `Pacific/Kiritimati` (UTC+14, no DST), `UTC`.
- `app/test/notifications/reminder_fire_time_property_test.dart` — a sweep across every day of a full year in a DST zone × several chosen times: the result is always strictly after `now`, its local wall time equals the chosen time (modulo the pinned gap rule), and its civil day is `today` or `today.addDays(1)` — the fire day never drifts.
- Round-trip vector: the DTO ↔ `TZDateTime` transcription is identity — the value T01's live impl rebuilds equals the instant derived here, including across the fall-back ambiguity row.
- Host-independence check: the vector suite re-run under different process `TZ` values produces identical results (eng-07 §7 T4/T5 method) — proving nothing in the path reintroduced the ambient zone.
- Clock-edge guard: the CI grep gate (eng-07 §5) extended to this module fails the build on `DateTime.now()` / `TZDateTime.now` / `tz.local` in the fire-time path.
- Offline guard: the shared throwing-`HttpOverrides` bootstrap is installed; any socket attempt from this suite is a loud, named failure.
