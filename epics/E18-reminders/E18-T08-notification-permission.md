## Goal

The OS notification permission (Android 13+ `POST_NOTIFICATIONS`, iOS authorization) is requested **in context — only at the moment the user explicitly opts into the reminder** — never up front, never batched into onboarding, with the honest one-line rationale already on screen. Denial is met with a **calm, non-obstructive state**: the row's switch stays truthful (no reminder is shown as "on" when nothing can fire), one quiet inline note explains, and the OS-settings path is *offered*, never forced. There is no nag loop — the OS dialog can only ever be triggered by another explicit user tap — and the rest of the app is entirely unaffected by a denial. The request/status/open-settings side effects live behind a new injectable `NotificationPermissionGateway` boundary with a deterministic fake, following `eng-define-service-boundary`. This task owns the request + denied/blocked UX only: the reschedule after a grant is E18-T05, the row scaffold is E18-T06, the fa/ckb/ar wording is E18-T10, and the `NotificationScheduler` itself is E18-T01.

## Implementation notes

This task is a boundary + a flow + one calm state. It computes nothing, persists nothing itself (the pref commit stays T03's), and schedules nothing (T01/T05). The dangerous failure modes are all UX-honesty failures — asking too early, nagging, or a switch that lies — so the flow invariants are pinned test-first with the fake gateway before any visual polish.

1. **Files.** The `NotificationPermissionGateway` interface + a small status type (`notRequested` / `granted` / `denied` / `permanentlyBlocked`) live framework-free beside the E18-T01 `NotificationScheduler` interface (value types only — no Flutter, no `dart:io` in the signature). The live impl lives with the shell's notification wiring; the Riverpod `Provider` gets a throwing un-wired placeholder and is overridden once in `main`'s `ProviderScope`. A deterministic fake (scripted status sequence; records every `request()` / `openSystemNotificationSettings()` call) ships for tests. The opt-in hook and the inline denied/blocked note widget live in the reminders feature beside the T06 row (e.g. `widgets/reminder_permission_note.dart`).
2. **Status semantics per platform.** Android < 13 has no runtime notification permission → the gateway reports `granted` by construction. Android 13+ needs `android.permission.POST_NOTIFICATIONS` declared in the manifest and requested at runtime via the already-approved `flutter_local_notifications` platform implementations — **no new permission package**; if the OS-settings launch turns out to need one, stop and file a decision-log amendment first (contract non-negotiable 17), never add it silently. iOS authorization, once denied, shows no second OS dialog → treat a prior iOS denial as `permanentlyBlocked`. No provisional/quiet iOS authorization: delivery the user never explicitly chose contradicts "opt-in is an explicit tap" (10 §9).
3. **The request fires only at the opt-in moment.** Flow: explicit toggle tap (T06) → read `status()` → if `notRequested`, call `request()` — the OS dialog appears *in context*, with the row's honest one-liner already visible as the truthful rationale → on `granted`, invoke the T03 enable path (persist-before-republish, then schedule). Never request at startup, at onboarding, on row build, on resume, or batched with anything else (10 §6). No custom "pre-permission" beg modal before the OS dialog — the in-context row *is* the rationale.
4. **Soft denial: calm, truthful, zero cost.** On `denied`: the T03 enable is never invoked (no pref commit, no `scheduleDaily`), the switch returns to off, and one quiet inline note renders beneath the row — `color.text.secondary` on the flat row surface, no `color.semantic.error`/red, no alarm icon, no dialog of ours to dismiss. Everything else on the screen stays fully interactive. A *later explicit* opt-in tap may request again — user-initiated only, never automatic.
5. **Blocked: never fire a no-op OS call.** On `permanentlyBlocked` (Android "don't ask again", iOS prior denial, or a revoked grant), an opt-in tap fires **zero** OS requests (a silently-swallowed dialog would be dishonest) and shows the note with a quiet secondary affordance — "open system settings" — that calls the gateway's settings deep-link (Android app-notification-settings intent; iOS app settings URL). The affordance is offered once, inline, ≥48dp; ignoring it costs nothing and no other surface repeats it (§11: obstruction is one tap, nagging is zero).
6. **The row never lies.** `enabled` is committed only after a grant, so the switch can never show "on" while nothing can fire. On app resume / row rebuild the gateway status is re-read: if the user granted in system settings, the note disappears (the reschedule is T05's); if a previously-granted permission was revoked, the row surfaces the blocked note rather than pretending a reminder is set.
7. **No nag loop — structurally.** The only call site of `request()` is the explicit opt-in tap handler; nothing requests from `build`, a rebuild, resume, a timer, or a listener. At most one OS dialog per tap. No banner, snackbar, or badge ever re-raises the permission unprompted.
8. **Strings are keys, not copy.** Register the ARB keys this flow needs (the rationale slot if any wording beyond the T06 one-liner is required, the denied note, the blocked note, the open-settings label) with base-`ar` placeholder values flagged pending E18-T10 transcreation + native/scholar review; no hardcoded user-facing text. Every value must already pass the banned-phrase gate — no guilt/fear/loss, no mandate words, no `!`.
9. **RTL + accessibility.** The note lays out with `EdgeInsetsDirectional`; the blocked state is signaled by text + a non-color glyph, never hue alone; one calm `Semantics` announcement for the note (the epic's DoD requires the denied/blocked state to be screen-reader legible); the settings affordance announces label + button role with a visible focus ring; OS text-scale respected.
10. **Pitfalls to avoid:** requesting at first launch or batching into onboarding; a custom beg-modal before the OS dialog; leaving the switch visually on after a denial; auto-re-raising the OS dialog on rebuild/resume; guilt copy ("you'll miss your revision", "don't lose your habit"); styling the denied note as a red error; gating any unrelated feature on the grant; adding `permission_handler`/`app_settings` without a decision-log amendment; calling the OS from the widget instead of the injected gateway; treating the settings deep-link as anything but optional.

## Acceptance criteria

- [ ] `NotificationPermissionGateway` exists as a framework-free interface + status type, a live shell-layer impl, a Riverpod `Provider` with a throwing un-wired placeholder overridden once at the composition root, and a deterministic recording fake — no view, controller, or widget reaches the OS permission API directly (verifiable by grep).
- [ ] The OS permission request fires **only** from the explicit opt-in tap: zero `request()` calls at startup, onboarding, row build, rebuild, or resume; the honest rationale (the T06 one-liner) is on screen when the OS dialog appears; no custom pre-permission modal exists.
- [ ] On a grant, the T03 enable path proceeds (persist-before-republish, then schedule via the injected boundary — asserted through T03's seam, not reimplemented here).
- [ ] On a soft denial: the switch returns to off, **no** reminder pref commits and **no** `scheduleDaily` fires, one calm inline note renders in `color.text.secondary` (no red, no alarm icon, no blocking dialog), and every other control on the screen remains interactive.
- [ ] On `permanentlyBlocked`: an opt-in tap fires **zero** OS requests; the note offers a single quiet ≥48dp "open system settings" affordance that calls the gateway's deep-link; ignoring it blocks nothing and nothing re-raises it.
- [ ] The row's displayed state is truthful across transitions: never "on" without an active grant; a grant made in system settings clears the note on resume (reschedule owned by T05); a revocation surfaces the blocked note.
- [ ] No nagging re-prompt loop exists: the OS dialog can only appear once per explicit tap; no timer, rebuild, resume, banner, or badge re-requests.
- [ ] Every string is an `l10n.*` ARB key (rationale slot, denied note, blocked note, settings label) flagged pending E18-T10 transcreation; no hardcoded user-facing text; all current values pass the banned-phrase lint in fa/ckb/ar.
- [ ] The note is RTL by geometry (`EdgeInsetsDirectional`), not color-alone (text + non-color glyph), screen-reader legible with one calm `Semantics` announcement, and the affordance has label + button role + visible focus ring; the five dark-pattern audit (10 §11) is recorded with no findings.

## Tests

All deterministic and offline: the fake gateway scripts every status, no real OS dialog is shown, the suite runs under a throwing `HttpOverrides` (eng-write-dart-test), and any date uses the injected `CalendarDate`. The flow invariants are written first.

- `features/test/reminders/notification_permission_flow_test.dart` (widget, **written first**) — the fake gateway records zero `request()` calls after pumping the row, rebuilding, and simulating resume; exactly one `request()` after the explicit opt-in tap; on a scripted `granted`, the T03 enable seam is invoked exactly once (a recording controller/repository double) — pins "request only on opt-in".
- `features/test/reminders/permission_denied_state_test.dart` (widget) — scripted `denied`: the switch is off after the flow, the recording repository shows **no** enabled-pref write and the T01 fake scheduler shows **no** `scheduleDaily`; the inline note is present, uses `color.text.secondary` and no error color/alarm icon; a sibling control on the same screen still receives its tap (no modal barrier) — pins "denial obstructs nothing and the row stays truthful".
- `features/test/reminders/permission_blocked_state_test.dart` (widget) — scripted `permanentlyBlocked`: an opt-in tap records **zero** `request()` calls; the note + settings affordance render; tapping the affordance records exactly one `openSystemNotificationSettings()`; not tapping it leaves everything functional — pins "offered, never forced".
- `features/test/reminders/permission_row_truth_test.dart` (widget) — scripted transitions across simulated resume: a grant made in system settings clears the inline note while this path itself records **zero** `scheduleDaily` calls on the T01 fake (the reschedule belongs to T05's reconcile); a scripted revocation after a prior grant surfaces the blocked note so the user is never shown a reminder that cannot fire — pins "the row never lies" across transitions.
- `features/test/reminders/permission_no_nag_test.dart` (widget) — after one denial, pumping N rebuilds, resume cycles, and elapsed fake time yields zero further `request()` calls without a new explicit tap; a second explicit tap yields exactly one — pins the no-re-prompt-loop invariant.
- `features/test/reminders/permission_banned_phrase_test.dart` (unit) — runs the never-ship banned-phrase lint over every ARB value this task adds in fa/ckb/ar (guilt/fear/loss, mandate words, "you'll miss"/"don't lose", `!`, emoji) and fails on any hit — the adab conscience check on the denied/blocked copy.
