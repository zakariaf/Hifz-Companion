## Goal

No view, controller, reconciler, or engine ever touches the OS notification layer directly: every schedule/cancel crosses one injected side-effect boundary. This task ships that boundary and nothing else: (1) a small **framework-free Dart `abstract interface class NotificationScheduler`** with exactly two verbs — `scheduleDaily` (consume an already-computed fire moment + already-localized strings, replace any prior schedule) and `cancelAll` — referencing value types only; (2) the **live implementation**, the SOLE place in the repo where `flutter_local_notifications`, `timezone`, and `flutter_timezone` are imported and `zonedSchedule(TZDateTime)` is called (engineering 07 §5's one edge exception; decision 14 — these three deps live in the app-shell scheduler only, never in the engine or the `CalendarDate` core); (3) a **deterministic hand-written fake** (no mock framework) that records calls and performs no IO; (4) the Riverpod `Provider<NotificationScheduler>` whose un-overridden placeholder **throws**, wired exactly once in `main`'s `ProviderScope`. T01 executes instants, it does not derive them (T04), persist anything (T02), orchestrate persist-then-schedule (T03), decide when to reconcile (T05), request OS permission (T08), or author a single user-facing string (T10). Notifications are strictly **local** — no push, no server, no socket, ever (PRD §14, C1).

## Implementation notes

This task is headless plumbing: no UI, no copy, no persistence, no clock read, no business logic. It moves values to the OS notification API and back — nothing more. The boundary shape and its tests come first; the live impl is a thin transcription layer.

1. **Files.** The interface + its value types + the throwing placeholder `Provider` live in one framework-free Dart file placed below the boundary per skill item 2 (models-level, beside the value types it references — final placement per the `02-project-structure.md` workspace layout), importing no Flutter, no `dart:io`, no plugin. The live impl and its wiring live in the `app/` shell (e.g. `app/lib/notifications/live_notification_scheduler.dart`), overridden in `app/lib/composition/providers.dart` from `main`.
2. **The interface is exactly two verbs.** `abstract interface class NotificationScheduler { Future<void> scheduleDaily(...); Future<void> cancelAll(); }`. `scheduleDaily` takes (a) the already-computed fire moment and (b) the already-localized title/body `String`s. No `TZDateTime`, no plugin type, no Flutter type crosses the interface. Every public member carries `///` docs stating the contract: schedule-replaces, cancel-is-total, local-only, no permission side effect.
3. **The fire-moment value shape is this task's contract with T04.** Define it beside the interface as a plain-fields value type (e.g. a `ReminderFireInstant` DTO: the resolved local wall-clock instant as integers plus the IANA zone id as a `String` — framework-free, `dart:core` only) with `///` docs naming it as the shape T04's pure derivation must produce. T01 defines and executes this value; it never computes one — there is no default, no "now + 24h" fallback, and no derivation logic anywhere in the boundary.
4. **The live impl is the sole home of the three decision-14 deps.** Only `live_notification_scheduler.dart` (and its init) imports `flutter_local_notifications`, `timezone`, and `flutter_timezone` — grep-verifiable. It resolves the device zone via `flutter_timezone`, transcribes the DTO 1:1 into a `TZDateTime`, and calls `zonedSchedule` with daily repetition at that local wall-clock time under **one fixed notification id** (so a repeat `scheduleDaily` replaces, never duplicates — the idempotent substrate T05 converges on). Android mode is `AndroidScheduleMode.inexactAllowWhileIdle`; `SCHEDULE_EXACT_ALARM` is never requested (decision 14). The impl requests no OS permission (T08) and contains no fallback copy (T10).
5. **Initialization is once, at the composition root, side-effect-quiet.** The plugin and the tz database initialize exactly once when `main` constructs the live service — never lazily on first schedule, never at import time; constructing the class performs no IO until a verb is called. Initialization failures flow into the same sealed error type as scheduling failures, not a crash.
6. **The `Provider` is the DI and nothing else.** `Provider<NotificationScheduler>` is a thin wire with zero business logic. Its default body **throws** (`StateError` naming the missing override) so a forgotten wiring is a loud startup failure, never silent null behavior (skill item 4).
7. **Wire once, in `main`.** The live scheduler is constructed only inside `ProviderScope(overrides: [...])` at the composition root — never lazily in a widget, never as a global singleton, never at import time (02-project-structure §2: `app/` computes nothing).
8. **The fake is a plain hand-written class** implementing the interface: it records every call `(verb, arguments)` in order into a public list, performs no IO, touches no plugin, and returns immediately — so T03/T05 tests can assert call order and idempotency by inspection. It may expose one scripted-failure switch so consumers can test the calm-retry path. Installed via `overrideWith`/`overrideWithValue`; no mock framework, no codegen (skill item 5).
9. **Failures are typed, calm, and copy-free.** The live impl defines one `sealed` error type (e.g. `ReminderSchedulingError` with `final` subclasses) surfaced to the feature layer; no error message shown to a user originates in the service, and the consuming surface renders a calm retry — never guilt/fear (skill item 8, PRD R3).
10. **No clock, no network, structurally.** The boundary contains no `DateTime.now()` — the fire moment arrives as a parameter (the injected clock is E02's; the derivation is T04's). No file in the boundary imports any networking package; notifications are local-only by construction, and push (which requires a server) is refused (skill item 9, PRD §14/§19.3).
11. **Pitfalls to avoid:** importing `timezone`/`flutter_timezone`/`flutter_local_notifications` anywhere outside the live module (the engine and `CalendarDate` core stay zone-free — 07 §5); deriving or adjusting the fire instant inside the boundary (T04's); deciding when to reschedule (T05's); persisting prefs or reading the DB (T02/T03); requesting the OS permission (T08); authoring or hardcoding any notification string (T10, and a localization-gate violation); business logic in the `Provider`; defaulting the provider to a live service instead of the throwing placeholder; a second notification id or a "while I'm here" extra schedule (an adab breach and a T05 convergence break); `DateTime.now()` anywhere in the boundary; a mock framework for the fake.

## Acceptance criteria

- [ ] `NotificationScheduler` exists as an `abstract interface class` with exactly two members — `scheduleDaily`, `cancelAll` — in a framework-free file that imports no Flutter, no `dart:io`, no plugin, no networking package (grep-verifiable); parameters are plain value types + `String`s only, each public member documented with `///`.
- [ ] The fire-moment value type is defined beside the interface with plain `dart:core` fields only and `///` docs naming it as the shape T04 conforms to; the boundary contains no derivation, default, or adjustment of any instant.
- [ ] The live implementation lives in the `app/` shell and is the **only** place in the repo importing `flutter_local_notifications`, `timezone`, or `flutter_timezone` (a grep over the workspace shows no other importer); it calls `zonedSchedule` with a `TZDateTime`, daily repetition, one fixed notification id, and `AndroidScheduleMode.inexactAllowWhileIdle` — no `SCHEDULE_EXACT_ALARM`.
- [ ] The live impl requests no OS permission, authors no user-facing string, persists nothing, and reads no clock — verifiable by inspection of the single file.
- [ ] The boundary is exposed as `Provider<NotificationScheduler>` with zero logic in the provider body; reading it un-overridden **throws** a named `StateError`.
- [ ] The live service is constructed exactly once, inside `main`'s `ProviderScope(overrides:)` via the composition root — no global singleton, no lazy construction in a widget.
- [ ] A deterministic hand-written fake implements the interface, records ordered `(verb, arguments)` calls, performs no IO, and installs via `overrideWith` — no mock framework anywhere in the task.
- [ ] The fake's scripted-failure switch completes the next call with the sealed error type, so T03/T08 can drive the calm-retry path against the same double.
- [ ] The plugin and the tz database initialize exactly once, at the composition root; constructing the live class performs no IO until a verb is called, and an initialization failure surfaces as the sealed error, never a crash.
- [ ] Failures surface as one `sealed` error type with `final` subclasses; no user-facing copy exists inside the service; catches are `on`-typed.
- [ ] No `DateTime.now()` and no networking symbol (`package:http`, `dart:io HttpClient`, `package:dio`) appears in any file this task adds.
- [ ] All added Dart passes `dart format --set-exit-if-changed` and `dart analyze --fatal-infos`.

## Tests

All deterministic and offline by construction: no wall clock, no plugin channel, no socket. The interface/fake/wiring tests are written before the live impl.

- `app/test/notifications/notification_scheduler_fake_test.dart` (unit) — the fake records `scheduleDaily` and `cancelAll` in call order with their exact arguments; a repeated identical `scheduleDaily` is observable as two recorded calls against the same fixed id (the raw material for T05's idempotency/convergence proofs); `cancelAll` after `scheduleDaily` leaves the recorded state cancel-terminal; the scripted-failure switch makes the next call complete with the sealed error, and the fake never touches a clock or IO.
- `app/test/notifications/notification_scheduler_wiring_test.dart` (unit) — reading the un-overridden `Provider<NotificationScheduler>` from a bare `ProviderContainer` throws the named `StateError`; with `overrideWith` installing the fake, consumers resolve the same fake instance (the provider added no logic and no wrapping).
- `app/test/notifications/notification_scheduler_offline_guard_test.dart` (unit) — runs under the shared throwing-`HttpOverrides` bootstrap (eng-write-dart-test): exercising the full interface surface against the fake opens no socket; any stray connection attempt is a loud, named failure, not a silent 400.
- `app/test/notifications/notification_scheduler_banned_import_test.dart` (unit) — a source-scan assertion over the boundary's files (interface, provider, live impl, fake): no networking import (`package:http`, `dart:io HttpClient`, `package:dio`) appears in any of them, and no file outside the live module imports `flutter_local_notifications`/`timezone`/`flutter_timezone` — pinning decision 14's placement as a test, in the spirit of the testing-strategy banned-import rule.
- Deliberately not tested here: the plugin channel's OS-level behavior (whether the notification actually fires) — a unit suite cannot observe the OS scheduler honestly. The cancel-then-reschedule convergence over these verbs is T05's test-first suite; the fire *moment*'s DST/timezone correctness is T04's frozen vectors; end-to-end delivery is exercised by the epic's device-level acceptance pass.
