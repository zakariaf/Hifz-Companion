## Goal

Ship `docs/verify-yourself.md` — the walkthrough that converts every trust claim into a step a stranger can independently check, treating auditability as a **deliverable, not a slogan** (13 §8). The doc carries exactly the four independent checks 13 §8 specifies, in order: **(1) verify the binary matches the source** — `gh attestation verify` against the published release artifact, *or* rebuild from the pinned tag with the pinned Flutter **3.41.2** and compare the AAB/APK hash (E20-T02's reproducible signed + attested build); **(2) verify "no data collected"** — read the single networking module in `packages/assets` (the ONLY code allowed a network import, CI-enforced), confirm one HTTPS GET of a public asset URL with no auth/cookies/identifiers, cross-check against Play "No data collected", Apple "Data Not Collected", and `PrivacyInfo.xcprivacy` (E20-T05); **(3) verify "offline forever"** — from first launch (the core muṣḥaf is **bundled**, no download) enable airplane mode and use Today · Muṣḥaf · Mutashābihāt · Progress · Settings with zero network, only optional reciter audio needing a one-time fetch (E20-T03's acceptance run); **(4) verify the muṣḥaf bytes** — re-derive each bundled asset's SHA-256 and compare to the manifest **baked into the binary** (11 §9; domain-asset-pack-integrity). This task is documentation only: it builds no gate and duplicates no sibling's machinery — it references them — and the writer must actually **run each check once** so the walkthrough is executable, not aspirational. Every privacy/offline/integrity assertion in the README or a store listing maps to a step here; an unverifiable claim is removed or rewritten. The claims it walks the reader through trace to **C-048** — traced, never originated.

## Implementation notes

This task writes one markdown file and runs four checks; it adds no screen, string, ARB key, CLAIM, workflow, or gate. Its correctness criterion is *executability*: every command, path, and hash in the doc must resolve against the real repo, because a stale or fabricated step in a trust document is worse than no document (13 §8 pitfalls; domain-adab-and-religious-integrity).

1. **File**: `docs/verify-yourself.md` — the exact path 13 §2's trust-pack layout names. It is covered by the `.reuse/dep5` bulk stanza for `docs/*` (no inline SPDX header needed); `reuse lint` must stay green. Written in plain, calm English like the other `docs/` artifacts — auditor-facing repo documentation, not in-app copy.
2. **Structure mirrors 13 §8 verbatim**: a two-sentence preamble (what auditability means for an offline, no-AI, no-telemetry app; the claims trace to C-048 and PRD §17), then the four checks in the specified order. Each check gets: *the claim being verified* → *the exact command(s) or observation steps* → *what output proves it* → *what a failure would mean*. No fifth check, no reordering.
3. **Check 1 — verify the binary matches the source (Android).** Two independent paths: (a) `gh attestation verify <app-release.aab> --repo zakariaf/Hifz-Companion` against the artifact published by E20-T02's `attest-build-provenance` step; (b) `git checkout` the exact release tag, install Flutter **3.41.2** stable (the pin of record), `flutter build appbundle --release`, and compare the SHA-256 of the result against the published artifact. Reference `release.yml` by path; do not restate its steps. State plainly that iOS is not byte-reproducible (Apple signing) — Android is where "rebuild the bytes" holds (13 §4).
4. **Check 2 — verify "no data collected".** Point the reader at the ONE file in the whole app allowed a networking import — `packages/assets/lib/src/live_asset_downloader.dart` — and at the CI enforcement they can re-run themselves: `bash tool/check_no_network.sh` and `bash tool/check_dep_allowlist.sh` (the three-layer gate, 11 §7). Instruct: confirm the module does one plain HTTPS GET of the pinned public asset URL with no auth, cookie, identifier, custom User-Agent, query param, or beacon. Cross-check the three declaration artifacts E20-T05 owns: `ios/Runner/PrivacyInfo.xcprivacy`, Apple "Data Not Collected", Play "No data collected".
5. **Check 3 — verify "offline forever".** From first launch: the core muṣḥaf is **bundled** — no download, no network in the critical path (2026-06-18 amendment; domain-asset-pack-integrity). Enable airplane mode and use Today · Muṣḥaf · Mutashābihāt · Progress · Settings; everything works. Note the one honest exception: optional reciter audio needs a single on-demand fetch, then offline again forever. Name E20-T03's acceptance journey as the automated twin of this manual observation — the doc links to it, it does not re-author it.
6. **Check 4 — verify the muṣḥaf bytes.** Two paths again: (a) run the repo's own gate, `dart run tool/verify_asset_hashes.dart`, which re-hashes the text, the 604 page fonts, the layout, and the mutashābihāt dataset against the binary-baked manifest **and** the authoritative Tanzil hash (11 §9); (b) manually `shasum -a 256` any bundled asset and compare against the constants in `packages/assets/lib/src/pinned_manifest_data.dart` — the same values compiled into the signed binary. State the trust-root rule explicitly: the manifest lives **inside the binary**, never a sidecar `.sha256` an attacker who can swap the pack could also swap.
7. **The claim-mapping audit.** End the doc with a short table: every privacy/offline/integrity assertion currently in `README.md` and the store listings (E20-T06's `fastlane/metadata/`) → the check (1–4) that backs it. Any assertion no check can back is **removed or rewritten at its source** in this task (that edit is in scope, flagged explicitly in the PR) — "we refuse claims a reader cannot check."
8. **Rot prevention, without a new gate.** The doc's header carries the review trigger verbatim from 13 §8: *reviewed whenever the build workflow, the networking module, or the manifest format changes*. This is a stated discipline plus a line in the PR template awareness — NOT a new CI job (that would trespass on E20-T01/T02's contract).
9. **Register (adab).** Honest and calm throughout: no superlatives, no "military-grade", no fear framing, no claim about retention/methodology (those live in the science screen, E19), no fiqh. The doc may state *what* the app refuses (telemetry, microphone, accounts) only because each refusal is checkable in the open source it points at.
10. **Pitfalls to avoid:** citing Flutter `3.38.0` from the docs' stale YAML examples (the pin of record is `3.41.2`); using 13 §8's placeholder repo slug instead of `zakariaf/Hifz-Companion`; inventing a command flag, path, or hash without running it; duplicating sibling machinery (re-specifying release.yml, the privacy manifest, or the acceptance journey); framing the sidecar checksum as acceptable; adding a fifth check or a CI gate; letting an unverifiable README/store claim survive the audit; any in-app string or ARB key (this task ships none).

## Tests

A documentation task — no code tests are added, and no gate is built. The Definition of Done demand is the **executable-walkthrough proof**: the writer runs each of the four checks once against the real repo and records the evidence (command + output) in the PR description, so the doc is known-runnable on day one.

- **Check 1 dry run** — `gh attestation verify` executed against an artifact from a T02 workflow run (or, pre-first-tag, the command validated against T02's completed `release.yml` with the real subject path and repo slug); the rebuild path validated by confirming the pinned tag + `flutter-version: '3.41.2'` in `release.yml`/`ci.yml` and building once locally.
- **Check 2 dry run** — `bash tool/check_no_network.sh` and `bash tool/check_dep_allowlist.sh` both exit 0; a grep for networking imports confirms `live_asset_downloader.dart` is the sole hit, matching the doc's claim.
- **Check 3 dry run** — E20-T03's airplane-mode acceptance journey green (`flutter test app/integration_test` on the emulator lane), plus one manual airplane-mode pass over the five surfaces on a device/emulator, observed and recorded.
- **Check 4 dry run** — `dart run tool/verify_asset_hashes.dart` exits 0 against the pinned manifest, and one manual `shasum -a 256` of a bundled asset (e.g. the Tanzil text file) matches its constant in `pinned_manifest_data.dart`.
- **Resolution check** — every relative link and file path in the doc resolves in the repo; the diff touches only `docs/verify-yourself.md` plus any claim rewrite the mapping audit forced (each such edit named in the PR).
