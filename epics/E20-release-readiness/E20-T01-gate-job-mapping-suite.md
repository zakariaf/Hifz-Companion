# E20-T01 — Assemble the PRD §20 gate→job mapping and the release-gate suite as one auditable contract

## Goal

The eight PRD §20 release-blocking gates become **one auditable, committed contract** instead of a comment. Today the gate→job mapping lives only as the comment block at the top of `.github/workflows/ci.yml` (lines 11–45) over five real jobs (`fast`, `date-matrix`, `golden`, `restraint`, `journeys`). This task **promotes** that comment into the canonical committed table specified in `docs/engineering/11-testing-strategy.md` §8 — a machine-readable `tool/release_gate_mapping.yaml` — and adds the completeness discipline: a meta-check (`tool/check_gate_mapping.dart`, run in `restraint`) that fails the build on any **orphan check** (a green step serving no named gate and not explicitly marked internal/advisory) or **orphan gate** (a gate row with no job), on a floating SDK (every job must pin the README baseline **Flutter 3.41.2** — *not* the docs' illustrative `3.38.0`), on any `continue-on-error`, and on any `--update-goldens`/`--update-vectors` in a workflow. Gates 1–6 are required machine-checks; gates 7–8 are **recorded human sign-off** rows that no CI job may claim green (E20-T09 records them). This task builds **no** gate machinery — the vectors/invariants are E04's, the manifest/verifier E05's, the golden harness E05's, the layered l10n gate E09's, the accessibility checks E08's — it *runs* them, maps each to exactly one gate, and proves the mapping complete. Authoring `release.yml`'s build/sign/attest is E20-T02; the airplane-mode acceptance run is E20-T03; DCO/reuse content T04; the human checkpoints T08/T09.

## Implementation notes

This task ships only a committed data file, one meta-check, its tests, and a surgical ci.yml edit. No product code, no screen, no string, no new gate machinery, no CLAIMS entry (nothing user-facing is authored — an empty CLAIMS delta is part of the contract).

1. **Files:** `tool/release_gate_mapping.yaml` (the canonical table); `tool/check_gate_mapping.dart` (the meta-check, run via `dart run` in the `restraint` job); `tool/test/check_gate_mapping_test.dart` + `tool/test/fixtures/gate_mapping/` (deliberate-violation fixtures); a minimal edit to `.github/workflows/ci.yml`. Both new `tool/` files carry the REUSE SPDX header (`GPL-3.0-or-later`), typed errors, `dart format` clean, per eng-add-ci-check §10.
2. **The mapping schema — one row per gate, plus explicit non-gate rows.** Each of the eight PRD §20 rows carries: `gate` (1–8), the PRD wording, `kind` (`machine-required` for 1–6, `human-recorded` for 7–8), `covenant` (the R1–R6 it defends), `jobs` (the ci.yml job names + the exact step/script names, e.g. gate 1 → `restraint`/`verify_asset_hashes.dart` + the runtime verifier noted as the device half), and `specified_in` (the doc §). Non-gate entries are explicit, never implied: `internal` (release-blocking but not one of the eight — token discipline per the design-docs, the pipeline wall, claims-register coverage, REUSE license clarity per 13 §4, the tool-gate meta-test suites, the E08 WCAG contrast audit), `advisory` (coverage publication, 11 §10), and `pending` (airplane-mode acceptance → E20-T03; DCO → E20-T04; privacy posture → E20-T05; build/sign/attest → E20-T02; sign-off artifacts → E20-T08/T09).
3. **Promote, don't duplicate.** Shrink the ci.yml comment block (lines 11–45) to a few lines pointing at `tool/release_gate_mapping.yaml` and keep the short per-job gate labels (e.g. `# gates 3, 4`); the YAML file is now the single source of truth. Two mapping sources that can drift apart is exactly the bug this task exists to kill.
4. **The meta-check's assertions** (each a named, loud failure): (a) every step in every ci.yml job matches exactly one mapping entry — an unmatched step is an **orphan check**, an unfilled `machine-required` gate is an **orphan gate**; (b) a step may serve exactly one gate (a check claiming two gates is a schema error); (c) every job resolves to the single pinned Flutter version, and that pin equals the README baseline (parse the README's "Flutter 3.41.2" line — one source, asserted everywhere); (d) `continue-on-error` appears nowhere; (e) `--update-goldens` / `--update-vectors` appear in no workflow (`update-goldens.yml` is the one documented exception — it is not a gate and is listed `internal` with that note); (f) no coverage-threshold flag appears; (g) gates 7–8 map to **no** CI job and are marked `human-recorded`.
5. **`release.yml` is touched read-only.** The meta-check additionally asserts release.yml's `flutter-version` equals ci.yml's pin and that it too has no `continue-on-error`/`--update-goldens` — but full gate-suite parity, build, sign, and attest are E20-T02's; do not edit release.yml here, and do not let the meta-check demand parity yet (T02 extends it).
6. **Confirm the dependency slots, add nothing.** Verify gate 5's row is E09's layered gate exactly as ci.yml already runs it (`check_l10n_complete.sh` + `tool/test/check_l10n_complete_test.sh` + the adab/ckb/plural suites in `restraint`; the analyze half and the per-locale RTL/numeral goldens in `fast`/`golden`; `date-matrix` as gate 5's date-correctness legs) and that E08's contrast audit sits in `fast` with the recorded accessibility pass referenced as its `recorded` half. If either is missing a piece, that is a **finding to raise against E08/E09**, not machinery to write here.
7. **Prove every gate against a deliberate violation** (eng-add-ci-check discipline), as fixtures, not by breaking the repo: fixture workflows/mappings with (i) an orphan step, (ii) a gate row with no job, (iii) a job pinned to `3.38.0` while the README says `3.41.2`, (iv) a `continue-on-error: true`, (v) an `--update-goldens` flag, (vi) a CI job claiming gate 8 — the meta-check must fail each with a message naming the gate/step; and one green fixture mirroring the real repo shape.
8. **Pitfalls:** "correcting" the 3.41.2 pin to the docs' illustrative 3.38.0 (the README baseline wins; the docs' YAML is an *abridged example*); deleting the ci.yml comment without committing the YAML first (never a moment with no mapping); letting the meta-check "fix" or regenerate the mapping (it only verifies — same verify-never-bless rule as goldens/vectors); marking a required gate advisory to go green; smuggling in any new gate, screen, or string under the release-polish banner (epic risk list); mapping the mutashābihāt **hash** (machine, gate 7's `restraint` half) as if it were the **sign-off** (human, T09) — the row carries both halves explicitly.

- [ ] The ci.yml comment block (former lines 11–45) is reduced to a pointer at the YAML plus per-job gate labels; no second free-text copy of the mapping survives anywhere.
- [ ] `dart run tool/check_gate_mapping.dart` runs as a `restraint` step and fails loudly on: orphan check, orphan gate, a step claiming ≠1 gate, any job pin ≠ the README baseline (3.41.2), any `continue-on-error`, any `--update-goldens`/`--update-vectors` in ci.yml or release.yml, any coverage-threshold flag, or a CI job claiming gate 7's sign-off half or gate 8.
- [ ] The pin is asserted from one source: the meta-check reads the README baseline and requires ci.yml's `FLUTTER_VERSION` and release.yml's `flutter-version` to equal it (all currently 3.41.2) — no hardcoded second copy of the version inside the meta-check.
- [ ] E09's layered l10n gate occupies gate 5's row exactly as ci.yml runs it (restraint script + meta-test + adab/ckb/plural suites, fast analyze half, golden RTL/numeral masters, date-matrix legs) and E08's WCAG contrast audit + recorded accessibility pass occupy their `internal, recorded` row — confirmed, with zero new machinery added by this task.
- [ ] Coverage remains published-only: the mapping marks it `advisory` citing 11 §10, and the deliberate-violation fixture proves the meta-check rejects a threshold gate.
- [ ] `release.yml` is unmodified by this task; the meta-check's release.yml assertions are read-only (pin equality, no `continue-on-error`, no golden/vector blessing) and currently pass.
- [ ] `tool/test/check_gate_mapping_test.dart` is wired into the existing `restraint` tool-gate suite step alongside the other meta-tests, so the meta-check is itself gate-proven on every PR, in the same lane as its siblings.
- [ ] No new screen, string, ARB key, CLAIMS entry, token, or dependency is introduced; the diff is the YAML, the meta-check, its tests/fixtures, and the ci.yml comment/step edit — nothing else.

## Tests

All deterministic and offline by construction: the meta-check and its tests read committed files only (workflows, README, mapping, fixtures) — no network, no clock, no device. Written first, per the gate-is-proven-against-a-violation discipline.

- `tool/test/check_gate_mapping_test.dart` (`package:test`, wired into the existing `restraint` tool-suite step) — **written first**, against `tool/test/fixtures/gate_mapping/`:
  - green fixture mirroring the real five-job shape → exit 0;
  - orphan-step fixture (a step in no mapping row) → fails naming the step;
  - orphan-gate fixture (gate 3 row with empty `jobs`) → fails naming the gate;
  - double-claim fixture (one step mapped to gates 1 and 6) → schema failure;
  - floating-SDK fixture (a job at `3.38.0` vs a README stub at `3.41.2`) → fails naming the job;
  - `continue-on-error` fixture, `--update-goldens` fixture, coverage-threshold fixture → each fails with its named message;
  - human-gate fixture (a CI step claiming gate 8) → fails: gates 7 (sign-off half) and 8 are `human-recorded`, never CI-claimable.
- Meta-check self-application (same test file): running `check_gate_mapping.dart` against the **real** repo files passes — which simultaneously pins that every job carries the 3.41.2 pin, that no `continue-on-error` or blessing flag exists in ci.yml/release.yml, and that the committed mapping and the actual jobs are in sync (the no-drift assertion this task exists for).
- One-off manual proof, recorded in the PR description (not committed): temporarily add an unmapped step to a ci.yml copy and run the meta-check → red; restore → green (eng-add-ci-check's deliberate-violation ritual applied to the real workflow shape).
